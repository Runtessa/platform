# IdpCore Architecture Map

This document is the working map for engineers and AI agents changing IdpCore. It focuses on ownership boundaries, runtime flows, and the safe order for future refactors.

## System shape

IdpCore is not a single web app. It is a multi-service tenant platform made of:

- **Core runtime**: tenant resolution, runtime APIs, registry, dispatch, ACL, adapters, and sandbox execution.
- **IDE / Studio**: authoring UI, editor, preview, publish flow, tenant/admin panels, assistant workflows.
- **Auth**: identity, OAuth/SSO, profile, org/role/user access context.
- **Kernel**: browser runtime that loads tenant UI packages from the Core registry.
- **Shared package**: TypeORM entities and cross-service contracts.
- **Infrastructure services**: monitoring, container-agent, codex-gateway, and VS Code extension integration.

## Repository map

- `src/core`
  - Express/TypeScript Core runtime.
  - Entry: `src/core/server.ts`.
  - API router: `src/core/app/routers/api.ts`.
  - Main controllers: `Dispatcher`, `RegistryController`, `ModuleController`, `UIEntityController`, `TenantAclController`, `OrchestrationController`, `AdminController`.

- `src/ideNew`
  - Next.js IDE and admin surface.
  - Main editor: `src/ideNew/src/pages/editor.tsx`.
  - Editor components: `src/ideNew/src/components/editor`.
  - IDE API routes: `src/ideNew/src/pages/api`.
  - Assistant/runtime code: `src/ideNew/src/lib/assistant`.

- `src/auth`
  - Next.js UI plus custom Express auth server.
  - Entry: `src/auth/server.ts`.
  - Domains: login, register, profile, admin access, OAuth, tenant SSO whitelist, org/role/user membership.

- `src/kernel`
  - Browser runtime source.
  - Main runtime: `src/kernel/src/index.ts`.
  - Route runtime: `src/kernel/src/routerRuntime.ts`.
  - Package cache: `src/kernel/src/packageCache.ts`.

- `src/public`
  - Runtime shell and preview assets.
  - `index.html` is the tenant shell.
  - `preview.html` bootstraps preview mode.
  - `bundle.js` is generated by the Kernel build.

- `src/packages/shared`
  - Shared entity and contract package.
  - Key entities: `Tenant`, `Module`, `ModuleRevision`, `UIEntities`, `UIPackageRevision`, `OrmModel`, `Secret`, `User`, `Team`, `PublishRequest`.

- `src/monitoring`
  - Monitoring ingest/service layer.

- `src/container-agent`
  - Docker/Podman management boundary used by IDE/admin tooling.

- `src/codex-gateway`
  - HTTP/SSE wrapper around Codex CLI workflows.

- `src/ide-vscode`
  - VS Code extension for tenant workspace sync, preview, and assistant workflows.

## Ownership boundaries

### Core owns runtime tenants

Core is the source of truth for tenant application runtime data:

- tenant hostname and runtime config
- modules and module revisions
- UI entities and UI package revisions
- ORM models
- ACL permissions, roles, and endpoints
- runtime secrets
- adapter access/config
- published registry artifacts
- runtime dispatch and sandbox execution

Core should not become an identity provider. It accepts identity/session context after Auth has done SSO/OAuth work.

### Auth owns identity and trust

Auth owns:

- login and registration
- cookie-backed auth sessions
- OAuth authorization code flow
- user profile
- user/org/role membership context
- tenant SSO whitelist and tenant OAuth clients
- tenant-aware access claims

Auth should not own full tenant application runtime config. It only stores enough tenant information to decide whether a tenant is allowed to use SSO/OAuth and how users map into tenant/org/role context.

### IDE owns authoring workflows

IDE owns:

- editor state and workspace UX
- draft save flow
- preview flow
- publish/staging/history workflows
- admin UI for tenants, packages, users, teams, monitoring, and containers
- assistant/codex workflows

IDE may call Core/Auth/infra services, but should avoid becoming the hidden source of truth for runtime records already owned by Core or Auth.

### Kernel owns browser runtime loading

Kernel owns:

- package resolution from registry responses
- package evaluation in the browser
- route manifest loading
- protected route session checks
- package cache and runtime style injection

Kernel changes must preserve the global boot contract: tenant shells expect `window.Kernel` and `new window.Kernel(...).boot()` to keep working.

### Shared owns contracts, not behavior

`src/packages/shared` should stay low-level and dependency-light. It should expose entities/types/contracts and avoid importing service/controller behavior from Core, Auth, or IDE.

## Public tenants and admin tenant creation

Public/general-purpose tenants are allowed and should stay public at runtime when their own config says so. The security boundary is different from tenant creation:

- Existing tenant apps may serve public routes and anonymous pages.
- A tenant may explicitly allow anonymous access through ACL endpoint config.
- A tenant may explicitly allow user registration through tenant/Auth policy.
- Kernel/runtime access to public UI packages should continue to work.

What must not be public is the **admin provisioning API** that creates or mutates tenants.

Recommended model:

- `/admin/*` is an operator/admin surface and must require an operator secret or stronger admin auth.
- Public self-service onboarding should use a separate endpoint/flow with:
  - hostname validation
  - reserved hostname protection
  - rate limiting
  - captcha or abuse protection if internet-facing
  - allowlist or approval when needed
  - bounded resource configuration
  - audit logging
- General-purpose public tenants should be modeled as tenant runtime policy, not as public access to admin APIs.

## Main runtime flows

### Tenant request dispatch

1. Request reaches Core.
2. `ContextMiddleware` resolves tenant from hostname.
3. `OptionalAuthGuard` or `AuthGuard` resolves session/user context when needed.
4. API routes handle `/api/*`, `/auth/*`, and selected admin routes.
5. Tenant app routes fall through to `Dispatcher`.
6. `Dispatcher` resolves the matching module or shared endpoint.
7. ACL is enforced.
8. `SandboxRunner` executes tenant code with adapters from `AdapterFactory`.

### IDE save/publish flow

1. Developer edits code in `src/ideNew` editor UI.
2. IDE calls Core APIs for modules, UI entities, ACL, or models.
3. Draft data is saved in Core-owned records.
4. Preview uses `src/public/preview.html` and Kernel source/bundle mode.
5. Publish creates revisions and marks artifacts as published.
6. Runtime non-dev paths consume published artifacts.

### Kernel preview/runtime flow

1. Tenant shell loads `bundle.js` or preview loads source mode.
2. Kernel asks Core registry endpoints for package metadata and source/compiled code.
3. Kernel evaluates packages with its runtime require/cache layer.
4. Router runtime handles route manifest and protected-route checks.

### Auth SSO flow

1. Tenant app redirects to Auth OAuth/SSO.
2. Auth validates tenant/client/user flow.
3. Auth redirects back to Core tenant callback.
4. Core exchanges/validates the response and creates a tenant session.
5. Runtime/API calls use Core session handling for tenant context.

## Integration points

- Core ↔ Auth
  - `CORE_SSO_AUTH_BASE_URL`
  - OAuth authorize/token/userinfo endpoints
  - tenant SSO whitelist and client provisioning

- IDE ↔ Core
  - `/api/modules`
  - `/api/ui-entities`
  - `/api/acl/config`
  - `/api/registry/*`
  - `/api/registry-tenant/*`

- Kernel ↔ Core
  - registry endpoints
  - `/api/auth/session` for protected routes

- IDE ↔ Monitoring
  - monitoring admin APIs and ingest service

- IDE ↔ Container Agent
  - service/container management APIs

- IDE ↔ Codex Gateway
  - assistant execution, workspace, and streaming routes

## Refactor hotspots

Prioritize small, behavior-preserving batches around:

- `src/ideNew/src/pages/editor.tsx`
  - very large editor page; extract hooks and state groups gradually.

- `src/kernel/src/index.ts`
  - large browser runtime; split package loading, runtime require, style injection, session runtime.

- `src/core/app/controllers/RegistryController.ts`
  - split catalog, package resolution, serialization, and cache concerns.

- `src/core/core/monitoring/MonitoringService.ts`
  - split middleware, client, pub/sub, and formatting concerns.

- `src/ideNew/src/pages/api/admin/tenants/[id].ts`
  - split validation, persistence, provisioning, and response shaping.

## Safety rules for changes

- Start every batch from a clean git status.
- Keep generated/build/vendor assets out of normal refactors.
- Preserve public APIs and runtime boot contracts.
- Prefer re-export shims when moving files.
- Run the smallest relevant build/type-check after each batch.
- Keep Core/Auth tenant ownership boundaries explicit.
- Do not move runtime tenant config into Auth.
- Do not make admin provisioning public to support public tenants; create separate public onboarding flows instead.

## Baseline checks

Current useful checks:

```bash
npm --prefix src/packages/shared run build
npm --prefix src/core run build
npm --prefix src/kernel run build
npm --prefix src/auth run type-check
npm --prefix src/ideNew run type-check
docker compose config
```

Known note: `npm --prefix src/kernel run build` can rewrite generated `src/public/index.html` formatting. Revert generated-only formatting changes unless the batch intentionally updates runtime assets.

## Suggested next phases

1. Build a stronger safety net around Core/Auth/Kernel behavior.
2. Document and test admin/public tenant provisioning separately.
3. Refactor SSO route files into small route/service units if needed.
4. Split `RegistryController` behind stable route handlers.
5. Split Kernel runtime internals while preserving `window.Kernel`.
6. Split IDE editor page by extracting hooks and state modules.
